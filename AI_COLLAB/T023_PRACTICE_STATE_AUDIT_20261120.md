
## Current answer-handler seam review (2026-11-20)
- **VERIFIED:** Hiragana quiz choice press checks whether a choice is already selected (the button becomes disabled), then calls the correctness predicate, updates selected-answer UI state, and appends `{character: question.prompt, correct}` to in-memory attempts. This is a single callback; there is no awaited persistence boundary today.
- **VERIFIED:** Row selection and `startPractice()` reset the attempts array and question index, so session identity must be generated at session start and attempt/event identity must be generated at the accepted answer, not inferred from question index alone.
- **INFERRED:** The persistence seam should accept an explicit immutable snapshot of the prompt (canonical script + character ID + displayed prompt metadata/content revision), choice outcome, presentation/answer timestamps, and generated event ID. It must not read mutable React state after the await. The user action callback will need an explicit async ordering contract to prevent UI advancement before durable write; test this callback with a fake writer before native DB integration.
- **UNKNOWN:** Full Katakana UI handler read remains unavailable via the GitHub file endpoint; current Katakana pure functions and earlier targeted audit establish its parallel local state shape, but no detailed handler ordering claim is made here.
- **Key correction to schema proposal (INFERRED):** Current kana practice uses static in-app character constants, not the synthetic SQLite glossary pack. Review-event content identity therefore should use a stable kana dataset/revision identifier plus canonical script and character key. A glossary-pack ID/version field can remain nullable/future-only for vocabulary review, or be replaced with a source-neutral content identity envelope. Avoid requiring a glossary pack identity for kana events.

## Expo SDK 58 SQLite write/transaction boundary (2026-11-20)

- **VERIFIED — versioned SDK API surface:** Expo's SDK 58 SQLite documentation describes `SQLite.openDatabaseAsync(databaseName, options?, directory?)`, `SQLiteDatabase.runAsync(source, params?)` for parameterized writes, and `withTransactionAsync(task)` with automatic commit/rollback. It also documents `withExclusiveTransactionAsync(task)` on Android/iOS/macOS/tvOS, passing a separate `txn` connection; queries in that callback must use `txn`, not the parent `db`. The exclusive method is explicitly unsupported on web. Source: https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/ (versioned SDK 58 docs currently show recommended package ~58.0.18).
- **VERIFIED — transaction hazard:** SDK 58 docs warn that queries on the same connection can join an active `withTransactionAsync` even when started outside its callback. Thus a shared DB handle with unrelated concurrent callers is unsafe unless access is serialized/owned; all migration work must be awaited and gated before repositories are exposed. The exclusive variant isolates callback queries but uses a new connection, so connection PRAGMAs/settings must not be assumed to carry over.
- **INFERRED — T023 minimal write path:** Open a dedicated app-owned learner-history database (never the bundled glossary DB) and keep one lifecycle owner/repository. For a single accepted answer, one parameterized `runAsync` INSERT is already an atomic SQLite statement; an explicit transaction is unnecessary unless multiple rows/projection changes must commit together. Stable event ID should be a UNIQUE/PRIMARY KEY. On retry, distinguish exact duplicate replay from an ID collision with different payload; do not silently treat every conflict as success.
- **INFERRED — migration path:** gate all consumers behind one awaited database initialization promise; read and validate `PRAGMA user_version`, reject a schema newer than the app, then perform schema DDL and its `PRAGMA user_version` update together in an awaited `withTransactionAsync`. Do not delete/recreate the history DB on migration failure. Serialize the initialization/other DB operations through the repository owner; do not launch unrelated writes during migration.
- **UNKNOWN — exact installed patch compatibility:** Project STATE records expo-sqlite 58.0.16, while the versioned SDK 58 documentation page currently recommends ~58.0.18. The documentation confirms the SDK 58 API family, but this audit has not inspected the installed 58.0.16 package typings/source or run native transaction tests. Before implementation, verify the exact lockfile-resolved package API and supported platform behavior. No API should be assumed solely from unversioned/latest docs.
- **Acceptance implications:** add tests for migration rollback/version atomicity; duplicate event replay and conflicting payload; concurrent answer writes; DB-open/migration failure; write rejection preserving the pending answer (no false saved state); app restart persistence; and platform transaction behavior. Use a fake repository seam for callback ordering first, then native integration tests. Do not add a dependency, change package pins, or alter the read-only glossary connection.

## Decision recommendation (INFERRED)
Prefer a serialized, single-owner writable learner-history repository. Keep event insertion to one parameterized statement with a unique event ID; reserve explicit transactions for migration and genuinely multi-statement atomic units. Do not default to `withExclusiveTransactionAsync` until exact 58.0.16 support and connection-level PRAGMA requirements are checked. Preserve failed attempts as visibly pending/retryable; only advance/mark durable after the repository confirms success.
